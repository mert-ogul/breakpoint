Breakpoint measures how inference delay, camera resolution, JPEG and H.264 compression, numeric precision, and device latency replay affect a robot policy's success in simulation. It runs a pretrained ACT policy on ALOHA TransferCube and a pretrained Diffusion Policy on PushT, each with paired seeds, and reports uncertainty for each condition.

## Render the saved report

Needs Python 3.11 and network access for the install. Rendering itself is offline and needs no simulator, Torch or model download. Run from a clone:

```bash
git clone https://github.com/mert-ogul/breakpoint.git
cd breakpoint
python3.11 -m venv .venv
.venv/bin/python -m pip install -e '.[report]'
.venv/bin/python scripts/render_benchmark.py \
  --input benchmarks/act-transfer/deployment-stress/data --out /tmp/breakpoint-report
```

Open `/tmp/breakpoint-report/index.html`. The renderer checks the saved files against their SHA-256 manifest and recomputes every count and interval before it writes anything. The committed report is at [`report/report.md`](benchmarks/act-transfer/deployment-stress/report/report.md); `index.html` in the same directory is the interactive version and needs a local browser.

## Results

Pretrained policy `lerobot/act_aloha_sim_transfer_cube_human`, ONNX Runtime on CPU. One stress axis changes at a time. Each condition is 30 paired episodes (env seeds 5000 to 5029). Entries are successes. The table is generated by `scripts/render_benchmark.py --update-readme README.md`.

- Baseline (ONNX FP32, native image, 0 ms delay): 25/30 (83.3%; Wilson 95% 66.4% to 92.7%).
- Constant added delay: first tested point below threshold is 320 ms at 18/30 (interval includes threshold).
- Camera resolution: first tested point below threshold is 60x80 at 10/30.
- JPEG quality: no tested point is below the threshold.
- H.264 bitrate: first tested point below threshold is 250 kbps at 19/30 (interval includes threshold).
- Numeric precision (categorical comparison, no ordering) against 0.8 x baseline: INT8 QDQ 24/30 not below; INT4 weight-only 23/30 not below.
- Device latency replay (categorical comparison, no ordering) against 0.8 x baseline: laptop-m3 replay 24/30 not below; rpi5 replay 9/30 below.

These are observed grid points, not exact boundaries. Thirty episodes per condition give wide intervals. The run is exploratory and has not been confirmed with fresh seeds. ## Supported scope

- ACT transfer (`lerobot/act_aloha_sim_transfer_cube_human`), ONNX FP32 with static QDQ INT8 and INT4 weight-only; Diffusion PushT (`lerobot/diffusion_pusht`), PyTorch FP32 only.
- Isolated axes: constant delay, resolution, JPEG, H.264 bitrate, precision, and laptop-m3 / rpi5 latency replay for ACT; constant delay, resolution and JPEG for Diffusion PushT. H.264 encode and decode happen in the same control step, with no codec or transport delay.
- Evidence from macOS 14.6 arm64 (Python 3.11, CPU) and a Linux aarch64 Pi profile; other platforms are untested ([compatibility](docs/compatibility.md)).
- FP16 and the H.264 deployment mode remain in the package outside the validated scope.

## Limitations

- Simulation only. The results say nothing about a physical robot.
- The rpi5 replay is one throttled Pi state. The firmware reported throttling or a temperature limit in almost every telemetry sample.
- INT8 is a static QDQ graph. It is not a full-model INT8 result and was not required to match FP32 numerically ([methodology](docs/methodology.md#export-and-validation)).
- INT4 stores 29 of 41 MatMul nodes as 4-bit blocks (61.6% of weight parameters); Conv, Gemm and activation MatMuls stay FP32, and weights are dequantized and computed in float. This is not a full-model INT4 result.
- H.264 is encoded and decoded in the same control step with no codec or transport delay, and the stream overshot the requested bitrate by up to 118.2 kbps.
- About 829 MB of raw evidence is not in the repository ([`large_evidence.json`](benchmarks/act-transfer/deployment-stress/data/large_evidence.json)).
